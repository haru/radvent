# 0001. Use Yarn as the sole JS package manager; drop package-lock.json

## Status

Accepted

## Context

The repository had two JS lockfiles committed at the same time: `yarn.lock`
and `package-lock.json`. Only `yarn.lock` was ever actually consumed:

- `Dockerfile` installs Yarn and runs `yarn install`.
- `build-scripts/install.sh` (used by CI, see `.github/workflows/build.yml`)
  runs `yarn install`.
- `AGENTS.md` documents every JS-related command (`yarn install`,
  `yarn lint:fix`, `yarn build`, `yarn build:css`) using Yarn.

Nothing in the Dockerfile, CI, or docs ever ran `npm install` or referenced
`package-lock.json`. It appears to have been generated by an incidental
`npm install` at some point and then kept alive because Renovate/Dependabot's
`npm_and_yarn` ecosystem manager updated both lockfiles together on every
dependency bump, masking the fact that it was unused.

Having two lockfiles for the same `package.json` risks them drifting out of
sync (different resolved versions/integrity hashes between `yarn.lock` and
`package-lock.json`), which is misleading for anyone who runs `npm install`
expecting it to be the supported flow.

## Decision

Standardize on Yarn as the only JS package manager for this project.

- Remove `package-lock.json` from the repository.
- Ignore `/package-lock.json` in `.gitignore` so it isn't reintroduced by an
  accidental `npm install`.
- Continue to commit and maintain `yarn.lock` as the single source of truth
  for resolved JS dependency versions.

## Consequences

- Contributors and CI must use `yarn` (not `npm`) for installing/updating JS
  dependencies, consistent with the existing Dockerfile/CI/AGENTS.md.
- Renovate/Dependabot should be limited to updating `yarn.lock` only; if a
  `package-lock.json` reappears from a tool run, it should not be committed.
- If the project ever migrates to npm, this ADR should be superseded rather
  than edited.
